A. ZAŁOŻENIA ARCHITEKTONICZNE (poprawione po red-team)
================================================================================

1. StudySessionEngine NIE jest UI - to czysty domain state machine.
   Trafia do domain/study/ i jest testowalny bez Androida.
   ViewModel study tylko wire'uje go do UI i callbackow TTS/STT.

2. Room z osobnymi tabelami (Groups, Cards, StudyModes, ActivityDays),
   NIE jeden JSON blob. Tylko SrsState i ModeStep trzymamy jako @ColumnInfo
   z TypeConverterem na JSON (kotlinx.serialization).
   Dzieki temu:
   - Atomowe aktualizacje SRS pojedynczych kart
   - Flow z Room reaguje tylko na zmiany w danej tabeli
   - Sync Firestore per-dokument (bez przepisywania calej talii)

3. CompoundStep - pelne wsparcie. Normalizer ogarnia zarowno AtomicStep
   jak i CompoundStep (normalizacja params + branchy). expandCompound()
   musi byc zachowane (compound -> lista atomic steps dla runnera).

4. Hilt jako DI (standard Android/Jetpack). @HiltViewModel dla ViewModeli.
   @Singleton dla Database, Repository, Services.

5. Error handling: Result<T> z metod repository. ViewModele trzymaja
   sealed class UiState<T> { Loading, Success(data: T), Error(message: String) }.

6. Firestore schema v2 - IDENTYCZNE nazwy pol i struktura dokumentow
   jak w starej apce (FirestoreDeckDoc, FirestoreCardDoc, FirestoreStudyModeDoc).
   Kotlinowa FirestoreSchema musi byc 1:1 portem firestoreSchema.ts.

7. Merge na loginie - tak jak stara apka: DeckRepository laduje lokalne dane
   z Room (natychmiast), potem w tle laduje z Firestore, merge'uje przez
   DataMerger, zapisuje do Room, emituje nowy StoreData przez Flow.

F. UWAGI IMPLEMENTACYJNE
================================================================================

1. KAZDY subagent dostaje prompt z:
   - Lista plikow do utworzenia (pelne sciezki)
   - Referencja do starego pliku/plikow TypeScript (co ma byc portowane)
   - Lista testow z istniejacego test suite (nazwy testow, expected values)
   - Kontekstem: jakie importy sa dostepne, jakie modele istnieja

2. Testy sa KLUCZOWE - subagent pisze je RAZEM z kodem, nie osobno.
   Testy dla domain NIE potrzebuja emulatora (JUnit 5, JVM).
   Testy dla Room potrzebuja emulatora (instrumentation).

3. Firestore schema MUSI byc binarnie kompatybilna z TS:
   - Te same nazwy pol (camelCase, nie snake_case)
   - Te same typy (number = Double w Kotlinie, timestamp = Long)
   - Te same nazwy kolekcji i dokumentow:
     users/{uid}/decks/{id}
     users/{uid}/cards/{id}
     users/{uid}/modes/{id}
     users/{uid}/activity/{date}

4. DI przez Hilt:
   - @HiltAndroidApp na RayCollApp
   - @AndroidEntryPoint na MainActivity
   - @HiltViewModel na kazdym ViewModelu
   - @Module + @InstallIn(SingletonComponent::class) na DataModule
   - @Singleton na Database, Repository, Services

5. Compose previews - kazdy ekran powinien miec @Preview composable
   z mockowymi danymi.

6. Material 3 - uzywamy M3 komponentow:
   TopAppBar, NavigationBar, NavigationRail, Card, ListItem,
   LazyColumn/LazyVerticalGrid, AlertDialog, FilledButton,
   FloatingActionButton, Slider, Switch, Chip, CircularProgressIndicator

7. Predictive back gesture - dziala z automatu przez Navigation-Compose
   (Android 14+). Nic nie trzeba robic - NavHost to zapewnia.
